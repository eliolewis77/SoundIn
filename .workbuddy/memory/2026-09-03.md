## 热力图在设置页消失（fix/heatmap-geometryreader-height，已合并 main）
- 现象：上一条「占满宽度」改动后热力图不显示。根因：外层 `GeometryReader` 在 Form/Section（底层 List 行）中被提议高度为 0 时，会把自己的高度报成 0，整行高度塌成 0、内容被裁掉。
- 修复：量宽度改为「背景 GeometryReader + WidthKey PreferenceKey」，VStack 仍按内容自然决定行高，宽度在背景单独量取、不参与布局。`cell` 由 measuredWidth 反推（占满一行、方形），未量到时退回最小值兜底。这是 List/Form 做宽度自适应的标准写法。
- 教训：**不要在 SwiftUI Form/List 行里直接把 GeometryReader 当外层布局元素**（会把行高撑成 0）；要量尺寸就用背景/overlay 里的 GeometryReader + PreferenceKey。
- 构建：沙箱拦 SwiftPM 写 ~/.swiftpm/security 导致的误报 failed，实际 EXIT=0、已重新签名。分支 fix/heatmap-geometryreader-height，commit d75fbbd，--no-ff 合并 main（a9445a3），重新打包重启（PID 47799）。

## PERF-5 统计页缓存 + 复用 DateFormatter（fix/perf5-stats-cache，已合并 main）
- 实测问题比原 review 描述更严重：`heatmapCells(weeks:13)` 一次渲染触发 91 次 `count(for:)`，而 `dateString` 每次都 `DateFormatter()` 新建（Swift 里昂贵操作）。加上 `totalCount` 每次全量快照 `UserDefaults`，合计约 99 次 UserDefaults 读 + 99 次 DateFormatter 新建 + 1 次 `dictionaryRepresentation()`；且每次成功听写 `objectWillChange.send()` 触发重绘会再来一遍。

- 正确性要点：`record()` 保持「写 UserDefaults → 清理 → invalidateCountsCache()」顺序，保证后续读（含日志里的 `todayCount`）拿到新值；清理用可能略旧的缓存键集合是安全的，因为只删除 90 天前、绝不会删当天键。

## PERF-6 文件日志常驻句柄 + 复用格式化器（fix/perf6-filelog-handle，已合并 main）
- 实际开销比记录更糟：每条日志 = 新建 ISO8601DateFormatter + 一次文件 stat(轮转检查) + open + seekToEnd + write + close。
- 改法（`Sources/HotkeyInputManager.swift` 的 HotkeyFileLog）：常驻 FileHandle（打开一次持续 append，仅轮转时关闭重开）；用累计字节数 knownSize 代替每条一次的 stat，仅在打开句柄时按真实大小校准；复用格式化器；轮转语义不变（>5MB 先删旧 .old 再把当前文件改名 .old）。
- **Swift 6 并发坑**：格式化器一开始写成 `static let`，编译报 error「static property 'stampFormatter' is not concurrency-safe because non-'Sendable' type 'ISO8601DateFormatter' may have shared mutable state」。这是真实竞争不是误报——`log()` 可能从主线程或网络回调线程发起，而 ISO8601DateFormatter 非线程安全。最终改为**实例属性 + 把时间戳生成挪进串行 queue**（只在队列内访问），而不是用 `nonisolated(unsafe)` 静默。副作用：时间戳记落盘时刻而非调用时刻，微秒级，诊断日志无影响。
- 验证方式（可复用）：重启 App，它会写 `=== app launched ===`；比对日志行数与末尾内容，确认追加而非覆盖、时间戳格式正确。实测 172→176 行，新增 4 条。
- 分支 fix/perf6-filelog-handle，commit 82f4ac6，--no-ff 合并 main（5653848），重启后 PID 51737。

## PERF-7 限流器 release 不再 fire-and-forget（fix/perf7-limiter-release，已合并 main）
- 位置：`Sources/SpeechManager.swift` 的 `transcribeSegment` + `TranscriptionConcurrencyLimiter`（limit: 2）。
- 原写法：`await acquire()` 后 `defer { Task { await release() } }`——defer 里不能 await，只能派发 detached Task。后果：槽位在函数返回**之后**才释放，而分段是并发转写的，后续排队分段会不必要地多等一轮，直接压低吞吐；且每次转写多一次 Task 分配调度。
- 改法：acquire 之后只有「成功 / 抛错」两个出口，用 do/catch 收敛成单一出口，再统一 `await release()`。取消路径同样会执行到释放点（actor 调用不受取消影响，会正常执行），不会漏释放。
- 分支 fix/perf7-limiter-release，commit 4720fae，--no-ff 合并 main（1ec729a），重启 PID 52389；冒烟验证启动日志正常（176→180 行）。
- **待真机验证**：限流器改动的实际效果要跑一次多分段听写（长录音触发分段并发转写）才能看出，暂时只能确认编译通过 + 启动链路正常。
- 踩坑：zsh 里 commit message 用双引号时，其中的反引号会被当成命令替换导致 `parse error near '}'`，整条命令不执行。改用 `git commit -F - <<'EOF'`（quoted heredoc）最稳。
